## AI-Team-Camp 為何比較容易完成

依使用者提供的 v1.9.1 學員包實際檔案比較；教材描述的流程不等於本次已獨立證明範本每項線上功能成功，也沒有時間數據足以保證 Study1 可在相同課堂時間完成。

教材並不是從空白即時發明整個預約系統：老師已提供包含試算表綁定程式、預約頁、LINE 登入、付款確認、到期處理及通知的完整產品。學員的主要工作是建立副本、授權、部署、填連線設定，再把預約元件接到網站。這是「安裝與設定現成產品」，Study1 則包含客製研究報名、同意與私人文件的產品開發。

教材也不是按一次就完成：它安排網站製作與上線、預約系統八步、網站接線及 LINE 設定，遇到登入／授權仍需使用者操作；最後另有試約及正式模式切換。可取之處是各步有明確輸入、完成畫面及接續點。

## 先前卡關的具體原因與責任

### 1. 管理身分與公開部署模型沒有收斂

`gas/AdminSandbox.js` 的 `study1AdminOwnerRequired_()` 同時比對 active 與 effective email。原部署為 ANYONE_ANONYMOUS／USER_DEPLOYING；後者代表以部署者權限執行，不代表每一位訪客都是部署者。

[Google Session 官方文件](https://developers.google.com/apps-script/reference/base/session) 說明，在未由訪客授權、以開發者身分執行等情境，active email 可能是空白；開發者本人或同 Workspace 網域另有可取得的情況。因此這裡存在部署與認證的結構風險。2026-11-22 最新紀錄確有 OWNER 拒絕，但沒有當次兩個 Session 值，不能斷言一定是 active 空白或只是多帳號問題。

教材把大多數管理操作放在試算表 UI，沒有要求所有管理設定都穿過匿名 Web App 的 Session。兩者同用 GAS，身分執行情境仍不同。也不能把教材的 `getEffectiveUser()` 初始化寫法搬到匿名管理入口，否則會錯認訪客。

改善優先處理「取得可靠管理身分」，再接私人設定。若正常 OWNER 工作階段仍不成立，應在既有系統設計可由伺服器驗證的管理認證；必須驗來源、目標、期限與 OWNER 身分，不能以刪 guard 或前端宣稱已登入代替。本次沒有實作認證替換或新增管理部署。

### 2. 程式已部署，正式設定卻晚到收尾才集中發現

進度記錄顯示第 11 版已發布後，才核對出正式映射、場次與預簽文件等尚缺；後續逐項補齊，又卡在 OWNER 與安全設定核驗。這是整合與交付次序問題，不能全歸因為 Google 權限。

應在開發早期就列全必要設定、來源、保存位置及誰能操作。使用者已核定的三場、72h、PDF 雙日期及 24h／2h 管理政策直接沿用；哪些已保存、哪些未核驗，依最新證據逐項記錄，不再把一般核准重新問一次。

### 3. 真正的發布來源與 raw gas 不相同

現行 client 先執行 `sameSiteCandidate()`，再套 `formalEntry.apply()`。程式還有 `replaceOnce()` 與來源 anchor 檢查。這能防止誤替換，但也使一般文案或功能改動受歷史基準及字串位置牽動。

最新進度記錄已有歷史摘要斷言、重複 HTML anchor 及正式／TEST 共用標籤造成的施工問題。處理方式應先找到正式產品所在層，保留已有效的組裝，不再增生一套新組裝器或為了舊固定摘要反覆搬移新功能。後續直接編輯產品來源的整理由受影響範圍逐步進行，不能現在整批刪保護或假稱已消除架構複雜度。

### 4. 過度追逐工程產物，壓縮了完成產品的時間

紀錄有發布工具改版、額外歷史錨點、稽核、合成 TEST 與大量驗證工作；部分有合理目的，但其存在與通過數不能證明參與者可完成正式報名。對此次任務，我應先交付端到端流程與完整設定，沒有必要把所有周邊工程都作為同一輪前置。

遵守目前不主動測試決策，保留自動 CI，不增加測試／證據平台；工程、部署、設定與使用者驗收分開回報。

### 5. 歷史錯誤被當成當期原因，本機版本也曾誤導判斷

原 README 仍寫初次複製狀態；本機多份副本落後遠端，部分又有未提交修改。我先前先看本機而未立即核對遠端，使說明沒有掌握最新接續點。這是我的來源選擇問題。

原發布鏈已有多次成功，V15 也已完成；不能再說「沒有發布工具／OAuth 尚未建立」。先前平台拒絕有真實原始紀錄，應保留其具體範圍及解除方式，不能改用別的入口規避，也不能擴大為所有文件／程式工作都不可進行。

## 現在改用的六步交付流程

1. **固定來源**：讀 main、最新接續點、直接受影響程式。這次使用 `study1-active` 乾淨工作副本承接原 repo；其他已有未提交變更的副本保留，不能直接覆寫或依名稱當最新。
2. **整段整合**：每次交付包含入口、畫面、伺服器、必要資料存取與錯誤恢復。既有 E1 核心已集中到 V15，先處理管理身分及設定收尾。
3. **集中發布**：沿用唯一工作流及原部署；這次只有文件，不再發布相同產品。未來程式變更由當期 preflight 取得 expected_head_sha／expected_version，再 publish 與回讀，結果不明先核實。
4. **管理身分**：取得可驗證 OWNER 的合法入口。無法確認則解決認證設計，不反覆重發或請使用者漫無目的換帳戶。
5. **集中設定**：按下表補齊實際缺項，保存後只回讀必要非敏感結果，不做額外報名、寄信或簽署測試。
6. **條件式啟用與交付**：核准及獨立啟用授權、管理身分與設定證據全部適用後，依原程序啟用並回讀。未驗功能標「已實作／已部署，功能驗收待使用者回饋」。

| 剩餘工作組 | 直接接續內容 | 已知狀態／完成依據 |

| OWNER 身分 | 管理呼叫者與執行身分的可靠驗證 | 最新紀錄仍拒絕；這次未重現或變更 guard |
| 資料表 | 原 personal／operations 私人映射與既有 schema | 有先前保存紀錄；當期值未重新回讀 |

## 是否廢除並重建

目前選擇改善原案：已有完整核心來源、原部署 V15 與先前隔離流程實作紀錄，尚未有證據顯示無法修復。現在換 repo、GAS 或 Sites 不會自動消除 OWNER 驗證、正式設定、PDF 與研究啟用需求。

若後續證明現架構在受支援且具適用權限的模式下確實無法滿足必要需求，才啟動使用者的條件式重建備案：先完成新產品與替換對應、保留必要歷史及資料、交代切換結果，再停止舊服務；廢除服務不等於刪除研究資料或任意撤銷保存政策。不得以新專案繞過原平台拒絕。

教材的私有程式沒有複製到這個公開 repo。本次改善的是工作方法與接續文件；沒有改應用程式、私人設定、場次、文件權限、部署或排程，也沒有宣稱修復了線上 OWNER 問題。
